١ Base Structure — Design Philosophy

١

Multi-Tenancy Isolation

الـ Tenant Detection والـ Dynamic Schema/Connection Strings كلها معزولة تماماً جوه الـ Infrastructure Layer. الـ Core Domain و Application ميعرفوش عن الـ Tenancy حاجة — هما شغالين في سياق Tenant واحد من غير ما يدروا.

٢

Standard Clean Architecture (Horizontal Slicing)

اخترتها لسرعة الـ Delivery. Projects بس — Domain, Application, Infrastructure, Presentation. أي Developer جديد يفهمها في يوم.

٣

Mini-Services Inside the Application Layer

بدل ما أعمل CQRS (تعقيد مش محتاجه دلوقتي)، بقسم الـ Application لـ Mini-Services صغيرة — كل Service ليها Interface و Implementation خاص بيها. بمنع الـ God Classes وأحافظ على Single Responsibility من غير Over-engineering.

٤

Feature Gating & Row-Level Security

مدمجة مركزياً في الـ Pipeline والـ Base Repositories. بتحكم في الـ Plans والباقات لكل Tenant من مكان واحد — مش هفضل أضيف if (tenant.Plan == "Free") في كل Controller.

٣ Core.Domain — System Nucleus

🧅

Core.Domain

الطبقة اللي ملهاش Dependency على أي حاجة — لا Libraries خارجية ولا Projects تانية

قلب النظام. لو اتغيرت الـ Database بكرة من SQL Server لـ PostgreSQL، أو الـ API اتغير من REST لـ gRPC، الـ Domain يفضل كما هو — مش بيتأثر بأي تغيير خارجي.

Common/
BaseEntity.cs — كل الـ Entities ترث منه. بيحتوي على Id (Guid), CreatedAt, CreatedBy.
BaseAuditableEntity.cs — يضيف UpdatedAt, UpdatedBy, IsDeleted للـ Soft Delete.
ITenantEntity.cs — عقد TenantId للـ Shared Schema Mode، الـ Repository يستخدمه للـ Auto-Filtering.
ValueObject.cs — Base للـ DDD Value Objects (زي Address, Money).
Entities/
Tenant.cs — Entity الأساسي للـ Tenant: Identifier, SchemaName, ConnectionString, SubscriptionPlan, Status.
User.cs — المستخدمين: Email, PasswordHash, IsActive, Roles[], TenantId.
Role.cs — Roles: SuperAdmin, TenantAdmin, Member.
Product.cs — Example Entity. كل Entity بيرث من BaseAuditableEntity.
Enums/
TenantStatus.cs — Active, Suspended, Trial, Expired.
SubscriptionPlan.cs — Free, Pro, Enterprise.
UserRole.cs — SuperAdmin, TenantAdmin, Member.
Exceptions/
DomainException.cs — Base Exception لكل Domain Errors. الـ Middleware في Presentation يمسكها ويحولها 400.
NotFoundException.cs — لما الـ Entity مش موجود → 404.

Core.Application

فيه كل Business Logic. بيعتمد على Domain بس — مش عارف مين البيستخدمه ولا الداتا بتتخزن فين

📂 Common/Interfaces/

العقود اللي Infrastructure هينفّذها:

IApplicationDbContext — عقد الـ DbContext.

كل Feature في فولدر لوحدها — Interface + Implementation:

٤+ Core.Application — Complementary Components

📂 Common/Mapping/

MappingProfile.cs — بيحدد كيف الـ Entities بتتحوّل لـ DTOs والعكس باستخدام AutoMapper أو Mapster.

مثال: Tenant → TenantDto، CreateTenantRequest → Tenant.

بيمنع الـ Services من إنهم يعملوا Manual Mapping متكرر. أي Entity جديدة — بتضيف Mapping ليها هنا بس من مكان واحد.

📂 Common/Exceptions/

ValidationException.cs — بتترمي لما الـ Input مش صحيح. الـ ExceptionHandlingMiddleware بتمسكها وتحولها لـ 400 Bad Request مع تفاصيل الـ Validation Errors.

ForbiddenException.cs — بتترمي لما User عنده صلاحية Authentication لكن مش مسموح له يعمل الـ Action ده (مش مسألة Token — ده بعد ما اتأكد إنه Authenticated). الـ Middleware بتحولها لـ 403 Forbidden.

📂 Common/DTOs/ — الـ Shared Data Transfer Objects

ApiResponse.cs
الـ Wrapper الموحد لكل Responses في النظام. الشكل: { Success: bool, Data: T, Message: string, Errors: List<string> } بدل ما كل Controller يرجع Format مختلف، كل حاجة بترجع نفس الـ Shape — سهّل على الـ Frontend يتعامل مع أي Response بنفس الطريقة من غير حالات خاصة.
PagedResult.cs
Wrapper للـ Pagination. الشكل: { Items: List<T>, TotalCount: int, Page: int, PageSize: int, TotalPages: int } الـ GenericRepository بيرجع الـ Items وبيحسب الـ TotalCount في نفس الـ Query — مفيش استدعاءين منفصلين لـ Database.

📂 Extensions/ServiceCollectionExtensions.cs

نقطة تسجيل كل الـ Application Services في الـ DI Container. الـ Presentation.API بتستدعيها مرة واحدة في Program.cs: builder.Services.AddApplicationServices(); جوّاها: تسجيل الـ Mini-Services كـ Scoped، AutoMapper / Mapster Profiles، Behaviors Pipeline. مفيش تسجيل Application Services في مكان تاني.

٥ Infrastructure — Multi-Tenancy & Data Access

🏗️

Infrastructure

تنفّذ كل Interfaces اللي اتعرّفت في Application. الـ Core مش عارف بحاجة من اللي هنا — ده العزل الصح

📂 MultiTenancy/ — ⭐ Multi-Tenancy Core

TenancyOptions.cs
⭐ يحدد Mode الـ Multi-Tenancy: SeparateSchema أو SharedSchema. بيتقرأ من appsettings.json → TenancyOptions.Mode. الـ GenericRepository و TenantInterceptor بيستخدمه لتحديد السلوك.
TenantProvider.cs
ينفّذ ITenantProvider. بيجيب الـ Tenant الحالي من HttpContext.Items — اللي حطه الـ Middleware.
SchemaService.cs
⭐ ينشئ Schema جديد لكل Tenant: CREATE SCHEMA tenant_{identifier}. بيرجع الـ Schema Name.
TenantConnectionService.cs
يدير Connection Strings. بيستخدم في حالات DB-per-tenant. مع الـ Schema-per-tenant الحالي مش مستخدم في الـ ApplicationDbContext — العزل بيتم عبر الـ Schema نفسه.
TenantStore.cs
Cache لمعلومات الـ Tenants. بيمنع ضرب الـ Database كل Request — بيستخدم ConcurrentDictionary (قابل للتبديل لـ Redis).
⚖️

فهم الـ Two Variants — Separate Schema vs Shared Schema

🟢 Separate Schema (الافتراضي — موصى به)

كل Tenant ليه Schema في نفس الـ DB • مفيش فلترة بـ TenantId • العزل بالـ Schema نفسه • HasDefaultSchema(schemaName)

🟡 Shared Schema (variant بديل)

كل الـ Tenants في نفس الجداول • فلترة أوتوماتيك بـ WHERE TenantId = @id في الـ Repository • ITenantEntity مطلوب

⚙️ بنحدد الـ Mode في appsettings.json → TenancyOptions.Mode. الـ GenericRepository و TenantInterceptor بيضبطوا سلوكهم بناءً عليه.

📂 Persistence/ — EF Core & Data Access

ApplicationDbContext.cs
الـ DbContext الرئيسي — دايمًا يشتغل على نفس الـ Connection String (Master DB). العزل بيتم عن طريق HasDefaultSchema(schemaName) في Separate Schema، أو عن طريق فلترة الـ Repository في Shared Schema. فيه الـ 3 Interceptors: Audit, SoftDelete, Tenant.
MasterDbContext.cs
DbContext خاص بالـ Master Database — فيه جدول Tenants بس (Identifier, SchemaName, Plan, Status). مشترك بين كل الـ Tenants.
Migrations/
Master/ 🟢 — لجداول الـ Tenants, Plans, FeatureFlags. بتتنفذ مرة واحدة على الـ Master DB.
Tenant/ 🟠 — لجداول البيزنس (Products, Invoices...). بتتنفذ لكل Tenant Schema جديد.
⚠️ دول مش نفس الحاجة. لو خلطتهم هتتخربط الـ Migrations.
GenericRepository.cs
Base Repository واعي بالـ Mode. في Shared Schema بيزود .Where(e => e.TenantId == currentTenantId) على GetAll, Find, Any وبيتحقق من GetById. في Separate Schema مش محتاج فلترة — العزل بالـ Schema نفسه.
Interceptors/
AuditableEntityInterceptor — Auto-set CreatedAt, UpdatedAt, CreatedBy, UpdatedBy.
SoftDeleteInterceptor — يحوّل Delete لـ IsDeleted = true.
TenantInterceptor — Mode-aware: لما Tenant يتضاف يحط TenantId أوتوماتيك. في Shared Schema بيمنع تغيير TenantId على Modified.

📂 Services/CustomLogic/ — ⭐ Per-Tenant Business Logic

لو كل عميل عاوز Logic مختلف (زي حساب الضريبة)، بنستخدم Strategy + Factory Pattern عشان نعزل الكود من غير IF/Else:

Strategies/
كل Strategy بتنفّذ Interface واحد (مثلاً ITaxCalculationStrategy).
StandardTaxStrategy — 10% للعملاء العاديين.
VodafoneTaxStrategy — 14% + 5 جنيه لعميل معين.
أي عميل جديد = Strategy جديدة — مفيش If/Else ولا تعديل في الكود القديم.
Factories/
TaxStrategyFactory — يستقبل Tenant ID ويرجع Strategy الصح. التسجيل في DI بيتم شرطياً حسب الـ Tenant.

📂 Services/FeatureGating/

FeatureGatingService.cs — بينفّذ IFeatureGatingService. بيشيك على Plan الـ Tenant: IsFeatureAllowed(tenantId, featureName). الـ Free Plan مش مسموح له يعمل Export — مفيش if في كل Controller.

📂 Services/Identity/

JwtTokenService.cs — ينشئ JWT Tokens (Access + Refresh). بيحط UserId, TenantId, Roles في الـ Claims.
CurrentUserService.cs — بينفّذ ICurrentUserService من HttpContext.User.Claims.
PasswordHasher.cs — BCrypt hashing عبر IPasswordHasher.

📂 Services/ — Shared Infrastructure Services

Services بتنفّذ Interfaces معرّفة في الـ Application Layer — مش بيزنس لوجيك، ده Technical Plumbing. كلها Cross-Cutting Concerns بيستخدمها أكتر من Mini-Service.

EmailService.cs
بينفّذ IEmailService. بيبعت Emails عبر SMTP أو SendGrid أو AWS SES — الـ Provider بيتحدد في appsettings.json. بيستخدم Templates لـ Welcome Email, Password Reset, Billing Invoices.
CacheService.cs
وينفّذ ICacheService. Wrapper على IDistributedCache (Redis أو Memory). Methods: GetAsync<T>, SetAsync<T>, RemoveAsync.
FileStorageService.cs
بينفّذ IFileStorageService. بيرفع وبيجيب Files من Cloud Storage (AWS S3, Azure Blob, أو Local في Development). Methods: UploadAsync, GetUrlAsync, DeleteAsync.

📂 Persistence/Configurations/ — EF Core Entity Configurations

كل Entity ليها Configuration Class منفصل بينفّذ IEntityTypeConfiguration<T>. بعيداً عن الـ Data Annotations — الـ Domain Entities نضيفة ومش فيها EF Attributes.

TenantConfiguration.cs
بيحدد Table Name, Column Types, Indexes للـ Tenants Table في الـ Master DB. بيعمل Unique Index على Identifier و SchemaName عشان يمنع التكرار.
UserConfiguration.cs
بيحدد Indexes على Email و TenantId. بيضمن إن الـ PasswordHash مش بيتعرضش في Queries عادية.
ProductConfiguration.cs
مثال على Configuration لـ Tenant-Scoped Entity. بيحدد Column Names وأي Precision محتاجها (زي Price decimal(18,2)).

📂 Persistence/Repositories/UnitOfWork.cs

بينفّذ IUnitOfWork. بيضمن إن مجموعة Operations بتتعمل كلها أو ولا حاجة (Atomic). Method واحدة: CommitAsync(CancellationToken ct) تستدعيها في آخر الـ Service.

٧ Pipeline Flow — The Request Lifecycle

Single Request Journey: From URL to Database
١

ExceptionHandlingMiddleware

أول حاجة بتستقبل الـ Request — بس هي أصلاً آخر خط دفاع. لو حصل Exception في أي حتة، ده اللي يمسكه ويحوله لـ JSON جميل بدل Stack Trace.

٢

RequestLoggingMiddleware

يسجل كل Request جاي — عارفين مين طلب إيه وإمتى. مفيد لـ Debugging و Monitoring.

⭐ TenantResolutionMiddleware

القلب. بيقرر مين الـ Tenant من Subdomain/Header/JWT. يجيب معلوماته من الـ TenantStore ويحطها في HttpContext.Items. كل اللي بعد كده بيقرأ من HttpContext.Items — مفيش استدعاءات متكررة للـ Database.

٤

Authentication & Authorization

JWT يتأكد من صحة الـ Token. Authorization يشيك على Roles/Permissions.

٥

Controller → Service → DbContext

الـ Controller يستدعي Mini-Service. الـ GenericRepository و Interceptors يطبقوا الـ Tenant Filter. الـ DbContext يستخدم Schema الصحيح — Security in Depth.

🔒

Security in 3 Layers:
1. TenantResolutionMiddleware — Resolves the current Tenant.
2. ApplicationDbContext — Operates on the same DB; isolation by schema (Separate) or filter (Shared).
3. GenericRepository — (Shared Schema) auto-appends WHERE TenantId on every Query.
